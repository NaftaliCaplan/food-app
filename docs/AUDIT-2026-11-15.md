## 🔴 Real bugs (not style — actual incorrect behavior)

**Both fixed 2026-11-15.** All 5 camera screens now gate `useVolumeShutter`'s `enabled` on `useIsFocused()` in addition to their own local state; `modules/volume-shutter/src/index.ts` now reference-counts native `startListening`/`stopListening` calls across simultaneously-mounted instances instead of each instance independently flipping the single global switch. 3 new regression tests added (`modules/volume-shutter/src/__tests__/index.test.ts`'s "multiple simultaneously-enabled instances" block). Full suite: 42/42 suites, 432/432 tests, `tsc`/lint clean. Still unverified on a real device (same native-module caveat as before).

### 1. ~~`useVolumeShutter` stays armed on backgrounded screens, causing ghost captures~~

`modules/volume-shutter/src/index.ts:119`'s own contract comment says callers should gate `enabled` on screen-focus state — but none of the 5 call sites actually do. React Navigation's native-stack keeps a screen mounted after a forward `navigate()` (no `unmountOnBlur`), so a screen that's been navigated away from (but not back-navigated) stays mounted underneath the new screen, with its state (and therefore `enabled`) often still `true`.

**Concrete failure**: `FoodCheckerScreen.tsx:49` — user types a label, captures, `navigate('Results', ...)` pushes a new screen. `FoodCheckerScreen` stays mounted underneath; `capturing` resets to `false` in `handleCapture`'s `finally`, `foodLabel` is still populated, so `canCapture`/`enabled` stays `true`. Pressing the physical volume button while viewing `Results` silently re-fires the hidden `FoodCheckerScreen`'s `handleCapture` — another photo gets taken off-screen and a second, unexpected `Results` screen gets pushed onto the stack. Same pattern at `AddItemScreen.tsx:76`, `LightCheckerScreen.tsx:46`, `SelfieCheckScreen.tsx:109`, `UserProfileScreen.tsx:87`.

**Fix**: gate `enabled` on `useIsFocused()` (or equivalent) at each of the 5 call sites, not just the screen's own local busy-state.

### 2. ~~`useVolumeShutter` has no reference counting — one screen's cleanup can silently disable another's still-active listener~~

`modules/volume-shutter/src/index.ts:129` — each hook instance independently calls `startListening()`/`stopListening()` on a single global native module, with no cross-instance counting. The iOS backing (`VolumeShutterModule.swift`'s `attach()`/`detach()`) is an unconditional on/off switch, not additive.

**Concrete failure**: given bug #1 above (multiple screens mounted simultaneously is the default, not an edge case), if one screen's `enabled` flips to `false` — its own local state changes, or it unmounts — its effect cleanup calls `stopListening()` → `detach()`, tearing down the one shared native interaction for *every* mounted screen, including a second screen whose React state still says `enabled: true`. The hardware volume button silently stops working for that still-active screen, no error, no re-arm until its own `enabled` toggles false→true again.

**Fix**: a simple refcount (module-level counter, only actually call native `startListening`/`stopListening` on the 0→1 and 1→0 transitions) would fix this independently of fixing bug #1, and should be done regardless since multiple simultaneously-enabled screens is plausible even after #1 is fixed (e.g. a future split-view or modal-over-camera-screen case).

*(Both verified by `/code-review`'s dedicated verifier agent against the actual file contents and React Navigation's real default mounting behavior — not speculative.)*

## 🟡 Readability / Naming / Cross-File Consistency

**No Critical findings in this category** — these are clarity issues a maintainer would trip over, not defects.

- **Naming drift in the capture flow**: `SelfieCheckScreen.tsx:69,85`'s real capture function is named `actuallyCapture` (wrapped by a countdown-aware `handleCapture`); every sibling camera screen names its one-and-only capture function `handleCapture` directly. Suggest `capturePhoto`/`runCapture`.
- **Duplicate type declaration across a prop boundary**: the identical `'preview'|'capturing'|'extracting'` union is independently declared twice under two different names (`Step` in `ReferencePhotoCapture.tsx:13` vs `CameraStep` in `UserProfileScreen.tsx:23`). Export one, import it.
- **Misleading service name**: `visionClient.ts:16`'s `callCloudflareVision()` calls the app's own proxy Worker, not Cloudflare directly (per its own header comment) — imported verbatim into all 4 checker families. Compounded by a second similarly-named file, `cloudflareVision.ts`, which now holds only `photoToBase64`. Suggest `callVisionProxy`.
- **Inconsistent "Service" file naming**: `cloudflareService.ts` (vendor-named), `tagService.ts` (domain), `selfieCheckService.ts` (domain+action), `lightCheckerService.ts` (domain+role) — no shared pattern, standing out against the perfectly-consistent "Analysis" sibling files (`foodAnalysis.ts`/`tagAnalysis.ts`/`selfieAnalysis.ts`/`lightAnalysis.ts`). Suggest `cloudflareService.ts` → `foodCheckerService.ts`.
- `foodAnalysis.ts:54` exports a bare `buildPrompt` while its 3 siblings export `buildTagPrompt`/`buildSelfieDetectionPrompt`/`buildLightPrompt` — gives no hint of domain at its import site.
- `selfieCheckService.ts:7` re-exports 3 names from `selfieAnalysis.ts` that nothing actually imports through (confirmed: `testing/run-selfie.ts:16` imports from `selfieAnalysis.ts` directly) — breaks the otherwise-consistent thin-wrapper pattern.
- ~~**Regression from the prior audit's own fix**: `SavedOutfitsScreen.tsx:29-34`'s `useFocusEffect` fires `getSavedOutfits().then(...)` with no `cancelled` guard~~ — **done 2026-11-15**, matching `WardrobeScreen.tsx`'s exact established pattern. 42/42 suites, 432/432 tests, `tsc`/lint clean.
- **Same problem, two different solutions**: `AddItemScreen.tsx:104-186` handles 4 post-capture steps as ~90 lines of sequential inline `if`-returns, where `UserProfileScreen`'s equivalent multi-step flow was extracted into `ReferencePhotoCapture.tsx`.
- **Unsafe cast from an avoidable type gap**: `navigation/types.ts:28`'s `OutfitResults.stylePrefs` is typed `string[]` instead of `StylePreference[]`, forcing `stylePrefs as StylePreference[]` at its one consumer (`OutfitResultsScreen.tsx:70`) for no reason — the real type is fully nav-param-serializable.
- **WHAT-not-WHY comments** (against this codebase's own strong, otherwise-consistent WHY-only convention): `AddItemScreen.tsx:104,116,133,158` and `UserProfileScreen.tsx:112,126` (comments restating the `if` condition below them); `utils/parseLLMResponse.ts:7,23,38,42,46` (5 plain WHAT labels, looks like it predates the convention); one branch in `foodAnalysis.ts:18`.

- `storage/wardrobeStorage.ts` domain-qualifies its CRUD function names (`addItem`/`removeItem`/`updateItem`); `outfitStorage.ts` doesn't (`saveOutfit`/`removeOutfit`) for the same shape.
- `modules/volume-shutter/android/.../VolumeShutterModule.kt:23-25`'s `isAvailable` returns unconditional `true` with no in-file comment explaining why no version-gate is needed (unlike its carefully-gated iOS sibling) — the rationale only lives in the TS consumer's comment. Also undocumented: Android keeps a persistent `armed` boolean on a wrapped callback while iOS adds/removes its interaction object fresh each time — likely a real platform-API difference, neither file says so.
