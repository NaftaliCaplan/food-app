# Codebase Audit — 2026-09-24

Full-codebase audit covering coupling/cohesion, duplication/bloat, dead code, test quality, readability, documentation currency, repo hygiene, disk usage, and API-key security. Conducted via three deep-dive passes (coupling/dead-code/duplication; test-quality/readability in services/utils/hooks; function-level efficiency across screens/components plus a dedicated efficiency re-read of services/utils/hooks) plus direct checks (security, docs, tooling, storage). Every finding below has a concrete file:line citation — nothing here is a vague impression.

This is a punch list, not a plan — nothing has been fixed yet. Work through it in whatever order makes sense; suggested prioritization is at the bottom.

## 🔴 Critical

### 1. API key ships inside the client app
`EXPO_PUBLIC_CF_ACCOUNT_ID` / `EXPO_PUBLIC_CF_API_TOKEN` (used by `cloudflareService.ts`, `tagService.ts`, `selfieCheckService.ts`) use Expo's `EXPO_PUBLIC_` prefix, which inlines their values directly into the client JS bundle at build time. The real Cloudflare Workers AI token currently ships inside the app itself — anyone who installs it (or unpacks the APK/IPA) can extract and reuse the real credentials under the user's account.

- **Not a git-exposure issue** — confirmed `.env` is correctly gitignored (`.gitignore`) and has never been committed or tracked in git history (checked via `git log --all --diff-filter=A`).
- **Is a client-bundling issue** — a server-side secret is being used with client-safe exposure semantics.
- Fix: a small server-side proxy/relay holding the real token; the app calls the proxy, never Cloudflare directly. Already logged as its own memory entry (`project_food-app_api_key_shipping_risk`) since the user flagged this as a pre-launch item, not urgent today.

### 2. `docs/ARCHITECTURE.md` is substantially stale
The doc's own stated policy is "update whenever a genuinely new subsystem lands (the outfit-generation rewrite would qualify)." ADR 0022 (Selfie Match Checker) is exactly that kind of change — a new feature, a deleted service, two renamed screens, three renamed components — and the doc was never updated for it.

Concretely wrong as of now:
- Lines 11–19: describes `clothesService.ts` → `ClothesCheckerScreen`/`ClothesResultsScreen` as a *live* legacy sub-mode. **These files no longer exist** — deleted in ADR 0022.
- Lines 76–77 (Screens table): lists `ClothesCheckerScreen`/`ClothesResultsScreen`, one marked "**Currently orphaned**." Both are false — renamed to `SelfieCheckScreen`/`SelfieCheckResultsScreen` and given a real `HomeScreen` entry point.
- Line 88: "Legacy-checker-only: `ClothesResultCard`... `ClothesStatusOverlay`" — these don't exist; replaced by `SelfieCheckResultCard.tsx`/`SelfieCheckStatusOverlay.tsx`.
- Line 96 (Services table): no mention of `src/services/selfieCheckService.ts` anywhere.
- Line 101 (Hooks): "`useAnalysis`/`useClothesAnalysis`" — `useClothesAnalysis` doesn't exist; replaced by `useSelfieCheckAnalysis.ts`, not mentioned at all.
- Line 119 ("Known quirks"): "The orphaned `ClothesChecker` route" — no longer true, it's a real reachable feature now.
- Also missing entirely: the three personalization rounds (ADR 0019–0021 — undertone/contrast/height/build all now feed `scoreOutfitAesthetics`, contradicting the doc's own claim elsewhere that `UserProfile` "feeds outfitService's currently-unused `profile` option").

### 3. `AGENTS.md` points future coding sessions at the wrong Expo version
Says "read the exact versioned docs at https://docs.expo.dev/versions/v56.0.0/" — the actually-installed package is `expo@54.0.35` (matches `package.json`'s `~54.0.0`). Following this instruction gets you API docs two majors ahead of what's real, which could introduce version-mismatched code.

### 4. `cloudflareService.ts` has zero test coverage
`src/services/__tests__/` contains `tagService.test.ts`, `selfieCheckService.test.ts`, `outfitService.test.ts` — no `cloudflareService.test.ts` exists anywhere. This is the food-checker's core service and the single largest coverage gap in the repo:
- `analyzeFood` (`cloudflareService.ts:69-128`) — success path, string/markdown-fallback path, non-OK HTTP path (`:100-103`) all completely unexercised.
- `adjustConfidence` (`cloudflareService.ts:13-25`) — real business logic (the >85 rescale, the <50kb/<150kb image-size caps) with multiple boundary conditions, zero tests.
- `foodLabelMatchesObserved` (`cloudflareService.ts:27-32`) — no test.
- Conspicuous because the two sibling services with near-identical shape (`tagService.ts`, `selfieCheckService.ts`) both have thorough tests with a directly-adaptable mock-fetch harness already sitting right there.

## 🟡 Function-Level Efficiency

Dedicated pass over every function body in `src/screens/` (12 files) and `src/components/` (16 files) — neither was covered by the earlier readability pass, which was scoped to `src/services/`/`src/utils/`/`src/hooks/` only — plus a re-read of that original scope specifically through an *efficiency* lens (the earlier pass checked readability, not performance). **Bottom line: screens and components are efficiency-clean.** Every list involved (wardrobe items, tag vocabularies, saved outfits) is small, nothing expensive is recomputed on render without `useMemo` where it'd matter, and the three screens that iterate item lists (`WardrobeScreen`, `SavedOutfitsScreen`, `OutfitResultsScreen`) are structurally consistent with each other (all use `useFocusEffect`-gated fetch + a `Map` for lookups, not a fresh scan per render). No manufactured nitpicks — the agent explicitly reported "fine" for entire files/folders rather than padding this section.

Two real findings, both in the logic layer:

- **Three independent copies of a char-by-char base64-encoding loop** (`cloudflareService.ts`, `tagService.ts`, `selfieCheckService.ts:55-62`) — each builds `binary += String.fromCharCode(bytes[i])` one byte at a time. Real, moderate severity: this runs on every photo capture (wardrobe item add, selfie check, food check), and captured photos can be hundreds of KB to a few MB, so it's a genuinely expensive loop on a hot path, not just duplicated code. Fix belongs alongside the existing "consolidate 3x Cloudflare scaffolding" item below — chunk the byte array (e.g. process in 8KB blocks) instead of one-char-at-a-time, while extracting the shared util anyway.
- **`outfitCandidates.ts`'s `selectBestOutfit`/`addAccessoriesGreedily` (lines 133-178) has no upper bound on combinatorial growth.** Base candidates ≈ bottoms × shoes × (tops + top-pairs), and *each* spawns an O(accessories²) greedy search that rescores the whole outfit every iteration. Rough estimate at 15 tops/10 bottoms/8 shoes/5 accessories: ~9,600 base candidates × ~25 rescores each ≈ a quarter-million `scoreOutfitAesthetics` calls for one "Generate Outfit" tap, synchronous on the JS thread. Fine for a realistic personal wardrobe (dozens of items per category) but has no ceiling — will visibly freeze the UI once any category grows past roughly 30-40 items. Not urgent (bounded by realistic use today), but worth a forward-looking guard (e.g. cap pairing/enumeration, or prune obviously-clashing pairs before forming candidates rather than after) before wardrobes get large. Related minor nit: `addAccessoriesGreedily` already computes the final candidate's exact score internally (line 86-91) but the caller (`selectBestOutfit:163`) recomputes it from scratch immediately after — cheap today, only worth fixing if the above is ever addressed.

Everything else checked and confirmed fine, not flagged for padding: `outfitAesthetics.ts`'s multiple short per-outfit scanning passes (outfit size is 3-6 items — merging them would save nothing meaningful and would hurt the current one-concern-per-block readability), `slotVariants`'s O(n²) pairing (correct shape for enumerating pairs, small n), all regex/parsing logic in the services layer (single passes over a handful of tags/garments), all hooks (thin async wrappers), and every component (`SelfieCheckResultCard`'s per-slot `.find()`/`.filter()` calls run over ≤3 fixed slots plus a handful of accessories).
